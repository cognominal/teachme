The mask and the scale

Two edits to one matrix — what a token may see, and how sharply it chooses.

Lesson 01 gave you four steps and one output. This lesson adds a fifth: before the softmax, the score matrix gets edited. That single place is the whole control surface of attention — masking, biases, windows and the scale all live there. You write three short functions in exercises/0002_masking.py and run ./bin/grade 0002.

Prerequisites: Lesson 01 — score, scale, softmax each row, mix the rows of V. If that page's checks pass, everything here is one new line of code. Shapes and the inner-numbers rule are Lesson 00. New to Python? The syntax map.

The one idea

Attention has exactly one place where you can change its behaviour: the (T × T) score matrix, before the softmax. Masking is not a special extra mechanism bolted onto attention — it is an edit to those numbers. Once you have that picture, a whole family of published tricks stops looking like a family.

1 · Where the fifth step goes

scores  = Q · KT / √dk   ← both edits happen here, on a (T × T) matrix
scores  = where the mask is 0: −∞
weights = softmaxrows( scores )
output  = weights · V
  1. Score. Q @ K.transpose(-2, -1) — unchanged from lesson 01.
  2. Scale. / dk ** 0.5 — unchanged.
  3. Block. New. Everywhere the mask is 0, replace the score with float("-inf"). scores.masked_fill(mask == 0, float("-inf")).
  4. Normalise. torch.softmax(scores, dim=-1) — still along each row. Rows now distribute their mass over the visible keys only.
  5. Mix. weights @ V — unchanged.

Order matters in exactly one place: the mask goes in before the softmax, never after. Blocking the scores first means normalising over the keys that are allowed, so every row is still a distribution summing to 1. Zeroing weights afterwards removes mass from an already-normalised row and leaves it summing to less than 1 — no longer a weighted average of anything. Whether you mask before or after multiplying by 1/√dk is irrelevant: −∞ × anything is still −∞.

2 · The score matrix is the whole control surface

Every published variation on attention is a rule about what to put in the cells of that (T × T) matrix. None of them change the matmuls.

Edit to the scoresWhat it buys
/ √dk (lesson 01)keeps the distribution soft as the width grows, so gradients survive
causal mask: j > i → −∞ (this lesson)a token cannot read the future — what makes next-token prediction possible
padding mask: pad positions → −∞variable-length batches: real tokens never mix in the filler. Same mechanism, different mask
sliding window: also block j < i − wa banded matrix — local attention, cheaper and still causal
add a per-head distance bias (ALiBi)position information straight into the scores, with no positional embeddings
one always-visible "sink" slotsomewhere harmless for a row to dump probability mass; used in streaming/quantised settings

And there is one thing you cannot do here: nothing in this matrix lets a token read a later row's value. The mask is a statement about the score matrix, and the score matrix is the only door.

3 · Why −∞ and not 0

The softmax is exp(score) / Σ exp(scores). So the filler you choose is really a choice of exp(filler) — the unnormalised mass you are handing to a token that must not be read. Here is the lesson's 4-token example, first row (the), with three different fillers in the six blocked cells:

Blocked scores set toRow 0 of the weightsBlocked cells exactly 0?
float("-inf") (or -1e9, or -1e4)[1.000, 0, 0, 0]yes — all 6 of them
0[0.378, 0.207, 0.207, 0.207]no — every blocked key keeps a share
-1[0.623, 0.126, 0.126, 0.126]no — just a smaller share

exp(0) = 1: filling with zero does not block anything, it invites every blocked token in at equal strength. exp(-∞) = 0: the filler has to drive the exponent below the point where float32 underflows to zero. That is why any large negative number works (exp(-1e4) is exactly 0 in float32) and 0 emphatically does not.

Three consequences worth keeping:

  • Exact zero, not nearly zero. The check in Part B tests weight == 0.0, not < 1e-6. A blocked cell contributes nothing to weights @ V — the future is arithmetically absent, not merely down-weighted. That is what Part C's leak test measures: replace a later value row with something absurd and the earlier output rows do not move at all.
  • Rows still sum to 1 — the blocked mass was never in the denominator. Measured worst error over 200 random causal draws in float32: 1.2 × 10−7, the same order as lesson 01's unmasked arithmetic.
  • A row must keep something. If every cell in a row is −∞, the softmax is 0/0 and the row becomes NaN. This is the padding-mask footgun: a fully-padded query position poisons the whole batch. Causal masks never do this — row i always keeps its own diagonal cell.
Watch it go wrong

Masking after the softmax is the mistake that looks harmless and is not. On this page's example the four row sums become [0.295, 0.524, 0.763, 1.0] — the rows no longer sum to 1, so the output is a weighted sum of the values with no claim to being an average of anything. Only the last row is unaffected, because nothing was blocked in it.

4 · The scale, now with numbers

Lesson 01 asserted that raw scores grow with dk and saturate the softmax. You can now see it, and you can see why masking makes it worse: a masked row averages fewer values, so what is left of the distribution matters more. Measured in this workspace (8 tokens, random normal inputs, mean of 20 draws) — the largest weight in a row, which is 0.125 if the row is perfectly uniform:

At dk = 64 an unscaled row is effectively a one-hot vector: one key takes 99.9% of the mass. softmax([8, 0, −8]) is [0.9997, 0.0003, 0.0000] — run it yourself. Scaling keeps the decisive-ness roughly constant as the width grows, which is exactly what a layer you intend to train wants.

7 · The same thing in production

Real code does not build the triangle by hand. F.scaled_dot_product_attention takes the intent as a flag:

import torch.nn.functional as F

out = F.scaled_dot_product_attention(Q, K, V, is_causal=True)   # the kernel applies the −∞ triangle itself

Checked, not asserted: in this workspace your five lines and that flag agree to within 3.6 × 10−7 in float32 across T = 1 … 17 (bit-identical in float64), and Part C of the checks compares your code against the kernel on every run.

This is the lesson where attention stops being a formula on a page and becomes the thing in model.py. Here is nanoGPT's CausalSelfAttention, unedited, minus the head reshaping that lesson 03 covers:

# in __init__: one triangle for the whole model, not a learned parameter
self.register_buffer("bias", torch.tril(torch.ones(config.block_size, config.block_size))
                            .view(1, 1, config.block_size, config.block_size))

# in forward:
att = (q @ k.transpose(-2, -1)) * (1.0 / math.sqrt(k.size(-1)))
att = att.masked_fill(self.bias[:,:,:T,:T] == 0, float('-inf'))
att = F.softmax(att, dim=-1)
att = self.attn_dropout(att)
y = att @ v

# ...or, on a GPU:
y = torch.nn.functional.scaled_dot_product_attention(q, k, v, attn_mask=None,
        dropout_p=self.dropout if self.training else 0, is_causal=True)

Three things to notice, each of which you can now read rather than guess:

  • The mask is a buffer: torch.tril(torch.ones(...)), registered once, sliced with [:,:,:T,:T] so it works for any sequence length up to block_size. It is not learned — it is the answer to "what is allowed", and that is a fact about the task, not a weight.
  • The order is exactly this lesson's order: scale, mask, softmax, mix.
  • The fused path replaces all five lines with one flag. When is_causal=True is available, the kernel never materialises the (T × T) triangle at all — and notice that nanoGPT's flash branch passes attn_mask=None, because the flag is the mask.

Why does a language model need this at all? Because training feeds it the whole sequence and asks for the next token at every position simultaneously. Position i must predict token i+1 without having seen it — otherwise the answer is already in the input, and the model learns nothing. Masking makes one forward pass give T honest predictions. It is also why generation can be cached: if a token can never look forward, the keys and values it looked at cannot change later (that is the KV-cache lesson).
