Lesson 03 · mission: write attention from scratch and make it work

Several weighted averages at once

Heads: the width is divided, not copied. And the only new skill is shape bookkeeping.

Lesson 02 left you with one (T × T) score matrix per layer. A real model has H of them, each computed over a slice of the width, then concatenated back together. That is the whole of multi-head attention — nothing in the score, the scale, the mask or the softmax changes. You write four short functions in exercises/0003_multihead.py and run ./bin/grade 0003.

Prerequisites: Lesson 01 (the four steps) and Lesson 02 (the mask). This lesson re-uses both, once per head. Shape intuition is Lesson 00; Python cramming is the crib sheet.

The one idea

A head is not a new mechanism. It is the thing you already wrote, on a narrower slice of the width, and it costs no more than the single wide version because each head's dot products are over C/H numbers instead of C. The paper's own summary of why anybody bothers: "Multi-head attention allows the model to jointly attend to information from different representation subspaces at different positions. With a single attention head, averaging inhibits this."

2 · The whole trick is one reshape

Every multi-head bug you will ever write is a shape bug. The split is two operations, and they do different jobs:

dh = C // n_head
heads = x.view(T, n_head, dh)      # (T, C) -> (T, H, dh): the width divides, nothing moves in memory
heads = heads.transpose(0, 1)      # (T, H, dh) -> (H, T, dh): heads become a leading axis

Why does the order matter? Because a (T, C) tensor's first axis is tokens. view(T, H, dh) re-reads the flat row of C numbers as H blocks of dh — that is the split. Only then is it meaningful to move the head axis to the front. The reverse merge is the same two steps backwards:

merged = heads.transpose(0, 1).reshape(T, n_head * dh)   # (H, T, dh) -> (T, H*dh) = (T, C)

Note .reshape rather than .view in that line. .view demands that the memory layout already matches the shape you ask for, and a transpose does not move anything — so this is the second-most-common error message in attention code:

RuntimeError: view size is not compatible with input tensor's size and stride (at least one dimension spans across two contiguous subspaces). Use .reshape(...) instead.

The message names the fix. .reshape copies if it has to; .contiguous().view(...) says the same thing out loud. (Whether .view raises depends on the strides — sometimes the two happen to line up — so a working .view proves nothing about your next reshape.)

This is exactly how the real thing is written. From nanoGPT's CausalSelfAttention, one line per role:

q, k, v  = self.c_attn(x).split(self.n_embd, dim=2)
k = k.view(B, T, self.n_head, C // self.n_head).transpose(1, 2)  # (B, nh, T, hs)
q = q.view(B, T, self.n_head, C // self.n_head).transpose(1, 2)  # (B, nh, T, hs)
v = v.view(B, T, self.n_head, C // self.n_head).transpose(1, 2)  # (B, nh, T, hs)
...
y = y.transpose(1, 2).contiguous().view(B, T, C)  # re-assemble all head outputs side by side

Same idiom, one extra axis: a batch of B sequences is a leading axis, so the heads go at position 1 instead of 0. On this page B = 1 and the batch axis is invisible — which is why the exercise works on plain (T, C) tensors.

3 · What the division buys

Multi-head is not "more attention for the same money" in some vague sense. Two measured facts about it:

  • It changes the answer, so it is a real change of function. On this page's example, one 4-wide head and two 2-wide heads disagree in the output by 0.0388 — comparable to the values themselves. A single (T × T) average per token is a bottleneck: everything the layer can move between positions has to fit through one distribution. "With a single attention head, averaging inhibits this."
  • It costs about the same. The paper: "we employ h = 8 parallel attention layers, or heads. For each of these we use dk = dv = dmodel/h = 64. Due to the reduced dimension of each head, the total computational cost is similar to that of single-head attention with full dimensionality." The QKT work is T²·C either way; the split just decides whether it is one T²·C matmul or H of T²·(C/H).

And there is a measured cost to getting the number wrong: the paper's Table 3 reports that "single-head attention is 0.9 BLEU worse than the best setting", while "quality also drops off with too many heads". GPT-2 keeps 64-wide heads like the paper and uses 12 of them (n_embd = 768, n_head = 12, so dh = 64) — that is the same shape nanoGPT trains, and the block you are about to read.

One caveat about what you are writing: the heads in your exercise are independent. Nothing mixes head 0's output with head 1's until a learned output projection WO is applied to the concatenation — in nanoGPT that is one line, self.c_proj(y). Without it, a head can only ever write into its own slice of the width. The checks test exactly that: change one head's slice of V and the other heads' output columns do not move by one bit.

6 · The same thing in production

Three additions separate your four functions from a trained model's attention block, and you have now seen all three:

  1. The projections are learned. Your exercise takes Q, K and V as given; a real block computes them as self.c_attn(x).split(...) — one linear layer producing all three, then split down the last axis.
  2. An output projection mixes the heads. y = self.c_proj(y), a learned (C × C) matrix over the concatenated heads. This is the WO in MultiHead(Q,K,V) = Concat(head1, …, headh)WO. It is what lets one head's finding influence what another head contributes downstream.
  3. The fused kernel takes the head axis directly. F.scaled_dot_product_attention expects (..., H, T, dh) and is_causal=True, so no mask tensor is built and no Python loop runs. On this page's example your per-head lines and the kernel agree to 1.2 × 10−7 (float32); the checks compare them on every run.

Beyond that, production varies how many key/value heads exist. Two verified papers: Shazeer's Fast Transformer Decoding: One Write-Head is All You Need (2019) proposes multi-query attention, where "the keys and values are shared across all of the different attention heads", to cut the memory bandwidth of incremental decoding; Ainslie et al.'s GQA (2023) generalises that to "an intermediate (more than one, less than number of query heads) number of key-value heads". Fewer K/V heads means a smaller cache to reload at every generated token — which is where this course goes next.
