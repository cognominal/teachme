## Workspace conventions

- **`HOW.md` is the map of the machinery** (page anatomy, the request → report → render flow, the checks contract, the checklist for adding a lesson, the traps). Read it before changing `tools/grader/` or a shared asset; keep it current when those change.
- Teaching matrices are arrays of rows — `[[..],[..]]` is `(rows × cols)`, matching the `(T, d)` prose in the paper. In Python this is `Q.shape == (T, dk)`.
- **The implementation lives in a real file, not in the page.** `exercises/<lesson>_*.py` holds the learner's code (stubs with the step list in comments); `exercises/solutions/<lesson>_*.py` holds a reference solution. Lesson pages carry prose, diagrams and retrieval practice only.
- The loop: `./bin/grade 0001` (terminal report), `./bin/grade 0001 --show-solution`, `./bin/grader` (local service + static server on 127.0.0.1:8757), `./bin/lesson 0001` (opens the lesson through the service if it is up), `./.venv/bin/python exercises/0001_attention.py` (the learner's own numbers, in a table).
- **`learning-records/` is gitignored** (notes about a person, not course material) and may legitimately be absent in a clone or a sparse checkout. **Nothing in the grading path touches it** — verified: no file under `bin/`, `tools/` or `assets/` reads or writes the directory, so a missing folder cannot break a script. The one script that owns it is `./bin/record` (`tools/record.py`), which `mkdir -p`s the directory before scanning for the highest number, so numbering starts at `0001` in an empty clone and keeps counting where the records left off.
- **Checks live in `tools/grader/checks/lesson_NNNN.py`** and are shared by the CLI and the service, so the terminal and the page can never disagree. Each part declares `entry`, `tests` and `diagnose` (ordered specific → general, last one `lambda fn: True`). Reference implementations live in the same file, written independently of `exercises/`. Add a lesson to `core.LESSONS` when its checks exist.
- Diagnoses are authored once in the page's HTML; the CLI strips tags (`cli.plain`).
- Tolerance: float32 chains land within ~4e-8 of float64, so `support.ATOL = 1e-5`.
- `support.max_diff` treats **identical non-finite values as equal** and a non-finite value on only one side as an infinite difference. This matters from lesson 02 on: `(-inf) - (-inf)` is `NaN`, so a naive comparison makes every masked-weights diagnosis unreachable (found by the variant suite, fixed 2026-10-21). Diagnoses that need a mask must use a probe where neither the mask nor its inverse fully blocks a row — a fully blocked row is `NaN` and cannot be compared at all.
- Assets are shared; a lesson must not re-implement them: `assets/matrix-view.js` (every matrix on screen, with `cellText`/`cellClass` for masked and diagonal cells — the CSS classes are `.masked` and `.self`), `assets/shape.js` (`Shape.product`, `Shape.explorer`), `assets/pyexercise.js` (fetches `/grade` and draws the verdicts; derives the solution filename from `spec.file` and the terminal command from `spec.lesson`), `assets/exercise.js` + `assets/tensor.js` (lesson 00's in-browser JS harness), `assets/quiz.js`, `assets/lesson.css` (the only stylesheet).
- Head bands (lesson 03): a heatmap cell can carry `.h0`…`.h3`, which set the `--tint` custom property that `.heatmap td` mixes into its shading; the pattern is a shade of the accent, not a new hue. `.head-key` is the little legend under such a grid.
- **The shipped `exercises/<lesson>_*.py` is the stub, and nothing else in the workspace holds a copy.** Before copying a solution over it to smoke-test the page's pass state, back it up (`cp exercises/000N_*.py /tmp/stub_000N.py`) and restore it afterwards; two lessons already cost a manual rewrite that way. Verify the restore with `grep -c NotImplementedError`.
- Before hand-off: `./.venv/bin/python tools/check_lessons.py` (parses every inline `<script>` and every asset with node — a stray quote in a lesson is otherwise only visible in a browser), then a Chromium smoke test of the real paths.
- **Browser smoke-testing gotcha:** `tab.run(async ({page}) => page.evaluate(...))` evaluates in an *isolated world*. Page globals are invisible (`PyExercise`, `Quiz`, `Exercise` are `undefined` there) and expando properties set by page code do not read back. Drive the real DOM instead: `#exercise .pyex-part`, `.feedback`, `.tests li`, `button.click()`, `textarea.value`, `data-passed`. DOM events do cross the boundary.
- Smoke tests worth repeating on any lesson change: open with the stub in place (expect failures + a named diagnosis), copy the solution over the learner file (expect "all parts pass" and matrices that say *your code*), restore the stub, then walk the quiz answer key by clicking.
- Grading the shipped stub must report `NotImplementedError`, not a crash; a solution in `exercises/solutions/` must pass via `--file` before it is offered to the learner.
